# Architecture Context — Intelligence Forge

## 1. Architecture Summary

The system has two primary workflows:

- **Ingestion:** uploaded research paper → document understanding → summary and entity/relationship extraction → Neo4j graph + Qdrant vector index.
- **Question answering:** user question → Qdrant knowledge-base search → optional Neo4j context enrichment → evidence-sufficiency evaluation → KB-grounded answer or privacy-reviewed web fallback.

The approved routing order is **knowledge base first, web fallback second**. Qdrant is the primary semantic retrieval interface. Neo4j stores explicit entity relationships and may provide graph context for retrieved knowledge.

## 3. Logical Components and Responsibilities

### 3.1 Frontend
- Provide document upload and ingestion-status experiences.
- Provide the research question-and-answer interface.
- Display structured answers, source attribution, and the answer source path.
- Communicate with the backend through REST APIs.
- Keep database, model-provider, embedding, and retrieval logic out of browser code.

### 3.2 API and backend
- Validate incoming requests.
- Orchestrate ingestion and question-answering workflows.
- Enforce the approved privacy boundary.
- Delegate persistence and provider operations to dedicated services/adapters.
- Return predictable response and error structures.

### 3.3 Document ingestion
- Validate uploaded files according to the active feature specification.
- Pass document content only through the approved document-processing path.
- Interpret text, tables, figures, images, and layout to the extent supported by the selected processing approach.
- Produce summaries and structured entity/relationship records.
- Validate model output before persistence.
- Preserve document and page/section provenance where available.

### 3.4 Knowledge graph — Neo4j
- Store extracted entities as nodes.
- Store extracted relationships as typed edges.
- Preserve stable identifiers and source provenance.
- Define labels, relationship types, constraints, deduplication, updates, and deletion behavior in the relevant feature specification before implementation.

### 3.5 Vector index — Qdrant
- Store embeddings generated by the selected embedding model.
- Index approved representations of entities and relationships.
- Store identifiers linking each vector record to its Neo4j record and source document.
- Define dimensions, distance metric, collection names, payload schema, and update/delete behavior after the embedding model and indexing requirements are selected.
- Do not treat a similarity score alone as proof that evidence answers a question.

### 3.6 Retrieval and answer routing
- Validate the user's question.
- Generate a compatible query embedding.
- Search Qdrant first.
- Optionally retrieve related Neo4j context.
- Evaluate relevance, coverage, provenance, and contradictions.
- Select a KB-grounded answer or a privacy-reviewed web fallback.
- Keep the original question available internally for answer relevance; do not automatically send it externally.

### 3.7 Web-search fallback
- Run only after the knowledge-base evidence is judged insufficient.
- Use only information allowed by the approved privacy policy.
- Never send uploaded files, extracted text, summaries, entities, relationships, embeddings, private metadata, or retrieved KB snippets to web search.
- Fail closed if a query cannot be shown to satisfy the approved privacy policy.
- Validate and clean provider results before answer generation.
- Preserve source URLs and metadata where available.

## 6. Privacy and Security Invariants

Treat the following as private paper-derived content:

- Original files and extracted text.
- Tables, figure descriptions, OCR output, and page content.
- Summaries and generated notes.
- Extracted entities and relationships when they reveal unpublished or sensitive paper content.
- Embeddings and vector payloads.
- Source metadata that could identify a private paper or project.

The web-search provider is an external trust boundary.

Required rules:
- Never send uploaded papers or paper-derived private content to web search.
- Never build external queries by concatenating KB results, summaries, extracted entities/relationships, vector payloads, filenames, or document metadata.
- Use only explicitly permitted outbound fields under the approved sanitization policy.
- If sanitization is uncertain or fails, do not call web search.
- Keep credentials server-side.
- Do not log private document content, raw extraction output, secrets, or unsafe outbound payloads.
- Test outbound requests using canary phrases from private test documents.
- Verify actual network paths and provider behavior before making privacy claims.

**Resolved local ingestion boundary (Feature 02):** Document parsing (`Docling`) and structured entity/relationship extraction (`Ollama` via `OLLAMA_BASE_URL`) execute 100% locally on the host machine. Uploaded PDF bytes, parsed tables, summaries, and extracted JSON artifacts never leave the local machine during ingestion.

## 7. System Boundaries

Keep these responsibilities separate as features are implemented:

- UI layer.
- API/controller layer.
- Ingestion service.
- LLM/document-processing adapter.
- Knowledge-graph repository.
- Vector repository.
- Embedding service.
- Retrieval and routing service.
- Web-search adapter.
- Answer-generation service.
- Shared schemas and configuration.

The web-search adapter must not receive raw documents, ingestion outputs, Neo4j records, Qdrant payloads, or private KB snippets.

## 8. Architecture Invariants

1. Search the private knowledge base before considering web fallback.
2. Never send uploaded papers or paper-derived private content to web search.
3. Fail closed when outbound-query safety cannot be established.
4. Ground factual KB answers in retrieved evidence.
5. Use Neo4j for explicit graph relationships.
6. Use Qdrant for semantic vector retrieval.
7. Link vector records to stable graph and source identifiers.
8. Validate uploaded files, model outputs, user inputs, and web results at boundaries.
9. Keep secrets server-side.
10. Preserve provenance wherever available.
11. Do not silently change approved architecture decisions.
12. Resolve deferred technology choices only when required by an active feature specification.
